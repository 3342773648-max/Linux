## x86_64 回归暴露的真问题（已修复）

### P0：containerd 安装失败——apt 缓存未刷新

- 现象：`apt install containerd.io` 报 `No package matching 'containerd.io' is available`
- 根因：`deb822_repository` 添加 Docker 源后不触发 `apt-get update`；arm64 时 VM 镜像恰有缓存
- 修复：`roles/containerd/tasks/main.yml` 在 `deb822_repository` 后添加条件 `apt update`（`when: docker_repo_state.changed`），首次部署源文件变化时刷新，重跑时跳过保持幂等
- 影响范围：arm64 无回归（已实测重跑 changed=0）

### P0：containerd config.toml 被本次测试所用 Ubuntu amd64 cloud image 预置禁用 CRI

- 现象：kubeadm init 报 `CRI: could not connect to the container runtime: unknown service runtime.v1.RuntimeService`
- 根因：**本次测试使用的** Ubuntu 24.04.4 amd64 cloud image 预置了 `/etc/containerd/config.toml`，
  内含 `disabled_plugins = ["cri"]`（禁用 CRI）；`containerd config default | tee` 有 `creates`
  守卫导致跳过（仅证明该 image 如此，不作「所有 Ubuntu amd64 cloud image 普遍预置」的泛化结论）
- 修复：`roles/containerd/tasks/main.yml` 在生成配置前检测预置 CRI-disabled 文件
  （`grep -q '^disabled_plugins.*cri'`），发现时 `file: state: absent` 移除（`notify: restart containerd`），
  后续 `creates` 守卫生效生成正确默认配置；修复完整性验证链为「移除→重启→kubeadm init 连接 CRI 成功→
  verify-cluster.sh 节点 Ready / 系统 Pod 正常」，证明 CRI 插件运行态可用而非仅文本修改
- 影响范围：arm64 无回归（arm64 image 无预置，检测跳过）；QEMU 重跑时 CRI 正常 → 不再触发

### P1：limactl snapshot 不可用（Lima 2.2.0 实验性未实现）

- 说明：尝试 `limactl snapshot` 保留 arm64 证据，返回 `fatal msg=unimplemented`
- 处置：改为不动 arm64 VM（保持运行）+ 独立 user-v2-x86 网段隔离（192.168.106.0/24 vs arm64 192.168.104.0/24）

## 与 arm64 验收的差异

| 项目 | arm64 (vz) | x86_64 (QEMU TCG) |
|---|---|---|
| 虚拟化 | Apple Virtualization (原生) | QEMU TCG 软件模拟 |
| VM 性能 | 接近原生 | ~20-30% 原生（tigera-operator 首次收敛需 ~30min） |
| 首次部署 changed | 9 (cp) + 4 (worker) | 10 (cp) + 3 (worker)（apt cache 更新多 1 次） |
| CRI-disabled 预置 | 不触发（arm64 image 无） | 触发（Ubuntu amd64 cloud image 有） |
| 架构断言 | aarch64 通过 | x86_64 通过（B0 首条路径） |
| 其余修复 | 无回归 | 无差异 |

## 遗留

- QEMU TCG 模拟性能使 tigera-operator 首次收敛较慢（~30min），非功能缺陷
- x86_64 回归验证建议后续在原生 x86_64 硬件或 VM 上复核以确认性能边界
